## Native responsiveness: the lean implementation plan

Otis can use the same API-level streaming behavior as a native harness while retaining its business-memory guarantees. It cannot promise identical Gemini consumer-app serving capacity, model routing or latency. Our basic direct Gemini 3.5 text probe produced first text at 4.6 seconds; the deployed model-list question took 21.8 seconds from acceptance to completion with a business-read/tool round. These are different prompts, so subtracting them would **not** measure Otis overhead. A matched baseline is required.

Use **Worker → existing workspace actor → provider stream → existing SSE/client**, with D1 at acceptance, business commands/checkpoints and completion, and Queue/cron for recovery/deferred work. Workflows may simplify a long background job if they replace code; they do not make this token path intrinsically faster. Continuous voice/realtime sockets, an SDK migration, a vector service or another orchestrator are unnecessary for recorded voice plus text replies.

Add one small structured timing record per run (no prompt/response bodies): accepted, actor start, context ready, provider request, response headers, first text/summary, first preview enqueue, tools/round count, final commit and delivery. On the client record local echo and first rendered text with one clock. Compare a short neutral reply, a read and a confirmed write using the same exact model/endpoint/effort/context/tools, cold and warm, direct and through Otis. Provider-only latency, app preparation, tool-loop latency and UI delivery are separate intervals; do not subtract timestamps from unsynchronized server/client clocks.

Proposed goals, **not measured guarantees**: local echo/control feedback under 100 ms; first provider text enqueued immediately without a database prerequisite; an established stream remains fluid without 400 ms artificial pauses; app overhead is a small fraction of the matched provider request rather than additional seconds of serial work. Record a small sample and median/tail results before choosing regional placement, provider tier or architectural migration. Provider stalls/outages need visible retry/model controls; lowering application overhead cannot remove provider queueing.
