## Why and current state

The web conversation is the home screen, not a CRM dashboard. A user must see an accepted message immediately, actual tool calls while the agent works, and a natural answer; after completion Working collapses but remains inspectable. All workspace members can read each other's chats, and only a chat's author can reply in it. The inbox and agent run exist after dependencies, but chats, transcript/read APIs, and a resumable activity stream do not.

## Scope

Modify chat/message/activity migrations, Worker /api chat routes, packages/contracts response types, shared slash-command registry/parser/dispatcher, and integration tests. Plan 008 owns rendering; plan 009 uses the same command services for Telegram; plan 010 owns binary voice upload. Do not expose raw provider chain-of-thought or put a dashboard API in the chat path.

## Data and API contract

Add chats(id, workspace_id, author_user_id, title, model_override_key nullable, created_at, updated_at), chat_messages(id, workspace_id, chat_id, author kind/user, channel, source_message_id, body, voice_ref/transcript nullable, delivery/run status, created_at), and run_activity(id, workspace_id, chat_id, run_id, sequence, type, tool/action ID nullable, public summary, structured safe detail, created_at). New chats inherit the workspace default model when override is null. Unique source message IDs and sequence per run permit replay. Message content and activity are not mutable to erase history; a correction or undo adds a new event/message state marker. Index member-authored chat text and final answers for workspace-scoped episodic retrieval; link memory entries to their source chat message IDs. On new chat creation and web/Telegram channel changes, the same workspace memory service remains available. Provide authenticated workspace/chat listing, paginated transcript, message send, status, action detail, action undo, clarification reply, and stream endpoints. Sidebar search may find chat titles/history; business-memory search remains a normal conversational message answered through query(spec), not a separate CRM screen. Return an opaque cursor for older pages and activity resumption. API returns server-validated membership and read-only flag for a teammate chat, but server checks author on every send regardless of UI.

Proposed same-origin route surface (names may be adjusted only once in packages/contracts): GET /api/workspaces/:workspaceId/chats; POST /api/workspaces/:workspaceId/chats; GET /api/workspaces/:workspaceId/chats/:chatId/messages?cursor=; POST /api/workspaces/:workspaceId/chats/:chatId/messages with client_message_id UUID and text; GET /api/workspaces/:workspaceId/chats/:chatId/runs/:runId/events?cursor=; GET /api/workspaces/:workspaceId/actions/:actionId; POST /api/workspaces/:workspaceId/actions/:actionId/undo; POST /api/workspaces/:workspaceId/clarifications/:clarificationId/reply for an optional suggested choice. The ordinary composer always uses POST messages; the server matches a conversational answer to the pending clarification without requiring a special control. An accepted send returns 202 with stable message_id and run_id; duplicate client_message_id returns those same IDs. Every route validates the workspace/chat/action relationship server-side.

Add GET /api/workspaces/:workspaceId/commands for the web picker's currently available command names and one-line descriptions, and GET /api/workspaces/:workspaceId/models for handpicked models whose provider has a configured workspace credential, their unique command keys, display names, voice capability, current workspace default and current-chat selection. Both require membership; a teammate's read-only chat cannot expose a switch action. POST messages remains the one send path. After durable inbox acceptance, a deterministic server parser checks the first non-space token for an exact supported `/name`, treats `//` as literal slash-prefixed text, and normalizes Telegram's optional `@<this bot>` suffix. It dispatches recognized commands before any model call. Persist the attributed command message, a `command`-kind execution/activity record when work is performed, and its reply so the existing transcript and stream can represent it without pretending a model ran. Unknown commands return a short help reply without a provider run or business write. The command registry and execution service live in shared `packages/commands`; web and Telegram adapters may format responses differently but cannot reimplement command behavior. `/workspace` switching must return an explicit destination workspace ID for web navigation, never change Telegram's active workspace, and record the command in the originating chat without moving earlier messages across workspaces. Dedupe command retries with the inbound external ID and action ID.

The shared registry initially contains `/model`, `/workspace`, `/today`, `/sheet`, `/undo`, and `/help`; `/sheet` is hidden until plan 012 is working. `/model` without an argument returns the current chat selection and available models; `/model <model-key>` writes an attributed, idempotent override for the author's current chat; `/model default` clears it. The key must be unique in the approved registry and its provider credential must be configured. A change affects subsequent accepted turns after the command, never an already running turn; snapshot exact provider/model ID in each agent_run. `/today` reads the saved brief/current due items, `/sheet` returns a fresh 15-minute link, `/undo` uses the same ledger service and dependency check as an action button, and `/workspace <name>` requires an exact unique membership match. `/start` is Telegram-only linking and is excluded from the web picker. Commands are shortcuts for normal conversation, not privileged model instructions.

Use one-way Server-Sent Events or an equivalent HTTP stream for current-run activity and message status. Persist every public activity event before broadcasting so reconnect with Last-Event-ID/cursor replays missed events exactly once in sequence. Types include accepted, queued, provider_started, tool_call_started/result, write_applied/action ID, thought_summary only if provider supplied and displayable, clarification_needed, partial_failure, answer, completed. Sanitize tool details: no keys, hidden prompts, full provider request bodies, or other workspaces' data. A final answer is a stored message; Working is its associated run. On a lost browser connection, server work continues from durable inbox/actor state. Client retries the same UUID, not a new send.

## Done criteria

The web can render one continuous transcript, live run status, per-write Undo, and teammate read-only chats entirely from API responses. The composer can list available slash shortcuts and submit them through the ordinary message route; the shared server dispatcher produces the same authorized result that Telegram will use. Every stream event can be reconstructed after reconnect. No model-internal text is exposed as thought unless supplied for display by the provider. A saved message and its execution status are distinct. All route tests enforce workspace membership.

## STOP conditions and maintenance

Stop if the selected streaming transport cannot replay after disconnect, if the actor can finish without persisting a final message, or if the API shape forces a teammate to impersonate an author. Keep transcript/activity storage bounded with pagination and retention policy; do not solve performance by deleting provenance.
