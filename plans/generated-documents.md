# R18 — Detailed documents, PDF creation and text/Markdown ingestion

Selected scope, 2026-10-10. Planned against `cc1076c` plus the working tree. Product/implementation plan only; no feature is shipped by this document. ## User outcome and concrete acceptance case

The user currently goes to Claude to create substantial multipage PDFs. Otis should do that from its own business memory, uploaded material and the user's instructions, then open the document inside Otis and support conversational revisions. PPT/PPTX is explicitly excluded for now. Markdown creation and text/Markdown ingestion remain part of the file foundation.

Acceptance request, supplied by the user:

> Hunor has asked for a practice session since he is travelling there tomorrow to meet with the gym guy and dancer girl in Cluj. Prepare an extremely detailed PDF for us to practice, preparing him for all the pitches, tactics, advantages, questions, bargaining and everything that comes along with it. We are hopping on a Google Meet call today to practice.

This is an example, not a hardcoded document type or special lead schema. Documents can also be proposals, meeting briefs, plans, reference guides or reports. Otis must decide useful structure and detail from the request. Do not create a gym/dancer PDF generator, a fixed CRM report, a dashboard, or a mandatory questionnaire.

For this example the useful result includes:

- A brief source-grounded account of both prospects, the meeting objective and what remains unknown. Resolve informal names using existing scoped lookup; ask only if genuinely ambiguous. Relative dates are resolved from the current request/member timezone, never hardcoded to this historical example.
- Separate preparation for each meeting: tailored opening pitch, discovery questions and follow-up branches, relevant advantages and realistic objections. Recommendations and hypothetical dialogue must be distinguishable from recorded facts.
- Negotiation preparation: questions before offering concessions, price/value framing, tradeable terms, possible next-step agreements and walk-away considerations. Never invent the team's costs, authorized discounts, prospect budget or promises.
- A usable two-person rehearsal agenda: who plays each role, timed practice rounds, difficult scenarios, realistic sample dialogue, feedback criteria and a second attempt after feedback. It should work during a call without requiring Otis to run the call.
- A concise meeting-day checklist, closing questions, next-step prompts and quick-reference pages. Unknown commercial details can be clearly marked for discussion instead of blocking all preparation.

Thorough means useful coverage and concrete material, not padding or an arbitrary page count. An 8–15-page guide is a reasonable visual fixture for this example, not a product minimum/maximum or a promise about model quality. Also prove a 25+ page fixture. Output language follows the request; mixed names, diacritics and longer translated text must work.

## Architecture and boundaries

Keep document authoring inside the existing agent tool loop. Add small typed file/document operations, not arbitrary shell commands or model-supplied executable HTML/JavaScript. Markdown is the retained, readable authoring source; PDF is an immutable rendered derivative. This gives Otis something to read and revise without re-extracting its own PDF or regenerating unchanged content.

Use R2 for original/source/revision/PDF bytes and D1 for scoped identity, source references, current revision and generation state. Use the current media byte-serving owner for downloads where compatible. Business records remain in the ledger; generated recommendations do not change them. A separately requested link to a client uses the existing attachment ledger command, with history/Undo. Chat-authored documents inherit their source chat's visibility until deliberately shared using an existing supported link; do not expose a personal-chat document merely because someone belongs to the workspace.

Rendering uses Cloudflare Browser Run's PDF Quick Action with controlled, fully assembled HTML. Official documentation supports HTML input, print sizing, headers/footers and resource blocking. Use a Worker binding if the installed tooling supports it; otherwise use direct REST with a narrowly scoped Worker secret and account configuration. Do not upgrade all runtime tooling to obtain an optional binding. Do not copy SDK method names from a different API version without checking the current endpoint. Reference: [PDF endpoint](https://developers.cloudflare.com/browser-run/quick-actions/pdf-endpoint/).

Cloudflare currently documents 10 browser minutes/day and one Quick Action request per 10 seconds on Workers Free. Check actual account entitlement before deployment; this plan does not claim account compatibility or cost compliance. Reuse the existing Queue for render work; respect Retry-After and delayed retries, no sleeping Worker or per-token DB polling. Reference: [limits](https://developers.cloudflare.com/browser-run/limits/) and [pricing](https://developers.cloudflare.com/browser-run/pricing/).

No PPT, Word editor, spreadsheet formulas, general filesystem UI, Python sandbox, new workflow framework, vector store, second agent loop, slide engine, arbitrary browsing or automatic outward sending. Do not add document templates for every business vertical. Layout components for headings, tables, quotations, lists and callouts are sufficient.

### D1 required UX — automatically attach oversized pasted text

Explicit user request, 2026-10-10: a paste that would exceed the 16,000-character message limit should become an ingestible text file instead of displaying a dead-end character-limit error. Implement this as part of D1, not a later optional polish task. Keep the inline message bound for existing transport/context costs; do not simply raise it or split a paste into several separately sent messages.

1. Handle plain-text paste in the production Composer using `clipboardData.getData('text/plain')`. Calculate the prospective value using the actual textarea selection: prefix + pasted text + suffix. Exactly 16,000 characters still works normally; only a prospective value greater than the current shared bound converts. Ordinary text paste, image clipboard handling and composition/IME remain intact. Do not treat a long pasted slash-prefixed document as a deterministic command or execute a partial command.
2. If the surrounding draft after replacing the selection still fits inline, create `Pasted text.txt` containing the **complete clipboard text**, preserving Unicode, paragraphs, whitespace and line breaks. Keep the surrounding instructions in the composer; place the caret where the selection was replaced. If the surrounding draft is itself too long, preserve the complete prospective combined message as one text attachment and empty the inline field. Never silently drop the selected replacement, original draft, end of the paste or existing attachments. Preserve intent and order explicitly when a paste occurred within existing text; the accepted message should record whether this was an inline replacement or a separate pasted context attachment rather than guessing later.
3. Show one normal attachment chip/card, 'Pasted text.txt', with preview/open and Remove, plus a quiet live announcement: 'Long text attached as a file. You can add instructions and send.' No modal, no manual download/reupload step, no mandatory confirmation, no separate paste composer. Preview must expose the complete text. Keep the filename plain; Markdown syntax remains readable inside a .txt file and can be processed as content.
4. Capture locally immediately; upload on Send through the same document flow. File-only Send is enabled and includes a trusted transport marker identifying an automatically attached long paste, so the agent reads it before responding and doesn't reply 'What should I do with this file?' when the user's pasted request already supplies the task. Deliver that content as part of user input, never system/developer instructions. Pasted quoted documents and embedded third-party instructions still do not gain authority to mutate records, fetch arbitrary links or expose secrets. Don't invent a user-written wrapper or claim the model already read it while uploading.
5. Share the file count/byte bounds with ordinary uploads. Measure UTF-8 byte length, not JavaScript character count, for the 2 MiB file limit. If file slots are full or the conversion cannot be accepted, preserve the text in a recoverable draft/attachment buffer and show a specific action, e.g. 'Remove an attachment to add this pasted text.' No trimming or silent conversion failure. Large pasted content must not be dumped into an unbounded textarea or repeatedly copied during typing. A storage failure keeps the local content accessible and shows the existing scoped storage warning; offer a download of the preserved text if recovery storage is unavailable.
6. Persist generated attachment bytes and their order/provenance alongside the scoped unsent draft using the existing IndexedDB ownership. Refresh/navigation must not erase them or leak them across account/workspace/chat changes. On Send freeze attachment bytes/IDs and one stable message UUID into the existing outbox ownership; upload/delivery retries reuse those identities. Clear only after the accepted local payload has taken ownership. A failed upload leaves the attachment and instructions retryable.
7. Treat conversion as one recoverable editing action: immediate Undo restores the replaced selection/draft and removes only that generated attachment; ordinary Remove must warn or restore access to its text so it cannot silently discard the user's only copy. Don't build a general undo engine; keep the minimal per-conversion local snapshot until the user makes further edits, sends, or explicitly discards it. A restored oversized draft has a visible 'Attach long text' recovery action. Also offer that action for already-saved/typed oversized drafts which never triggered paste; avoid converting text during each keystroke.
8. The agent receives a bounded descriptor and can read the retained text through `read_document`; no eager insertion of the entire long file into every provider round. It must retrieve enough sections to satisfy the request and disclose unread/partial coverage. Later follow-ups can reopen it without reupload. The long-paste path is not a license to skip the end of the user's request because only the first chunk was read.

Acceptance checks: paste 16,000 vs 16,001 characters; a selection replacement that stays under the limit; long paste into empty composer; long paste inside existing instructions; already-oversized surrounding draft; Unicode byte bound; attachment limit; two successive pastes; undo/remove recovery; refresh/retry/offline and account/workspace switches. Use a real native-browser paste to prove full text reaches the attachment and a local Worker/read tool check to prove Otis can ingest its final section. Check that the original 'Keep the message under 16,000 characters' dead end is replaced by this supported conversion path once D1 is implemented, without weakening server validation.

## Slice D2 — Substantial authoring and conversational revision

Owners: `packages/agent/src/{tools,prompt}.ts`, `apps/worker/src/agent/{repository,handler}.ts`, document repository/source reader, existing logical tool-step receipts and actor checkpoint owners only where required.

Provide a compact document authoring tool with start/write/publish operations (or three equally small explicit tools):

- Start: title, intended sections and optional existing document/base revision. Returns actual scoped IDs and available bounds.
- Write: one bounded group of sections with stable section IDs and their Markdown; replace those sections or add them in an explicit order. Code persists a logical-step receipt and digest. A repeated step replaces/replays exactly; it must not append duplicate prose. Tool returns IDs, revision state, saved section titles and lengths rather than returning the whole document.
- Publish: freezes a complete source revision and submits one PDF render job. Validate that intended required sections exist/nonempty. If content is incomplete/truncated, retain a draft and expose Resume; don't claim a finished detailed guide. Markdown-only output can publish without a PDF render.
- Read: use the existing bounded document-reading behavior for uploaded and generated source. Support discovery from the current chat and explicitly linked client, so 'revise the PDF you made yesterday' doesn't require reuploading or internal IDs.

The agent first retrieves relevant client dossiers, interactions, recent promises and necessary attached content using existing tools. It then writes useful sections over as many bounded rounds as needed. Keep the existing 4,096-token ordinary chat budget; section writing already permits documents larger than one output. If measured quality needs a larger authoring-round budget, gate it on a trusted active document draft, bound it to the pinned provider/model capability, and record usage; do not regex-match arbitrary mentions of PDF or globally increase chat limits. Preserve Stop, retries, checkpoints, deadlines and existing round limits. On a limit, leave a resumable draft with an honest message. Do not sneak in a second unaccounted model call or skip provider accounting.

Retain the request, outline and section completion summary across restart without replaying every full section into every provider round. Large tool arguments already enter durable checkpoints: inspect handler checkpoint compaction and avoid copying the complete source into tool results/context. Measure prompt growth as the document grows. Do not regenerate all prior sections each time an additional section is written.

Revisions use the referenced base revision. 'Make the objections section harder' retrieves/rewrites that section, keeps other sections, and produces a new version. A stale base asks narrowly or starts from the latest version; do not silently replace somebody else's revision. Preserve earlier versions with understandable 'Previous versions' access. Derived PDF failures never destroy their source. Generated document content stays an artifact, not canonical business memory.

Quality guidance: adapt length/structure to request; distinguish known facts, unknowns, assumptions and advice; use source references the code has actually verified. Hypothetical rehearsal lines can be invented as examples but cannot claim the prospect said them. Useful section titles, realistic dialogue, branch questions and concrete checklists matter more than generic motivational prose. No automatic deep web research unless needed/requested; no invented pricing or external claims.

Verify local replay/restart, exact-step duplicate prevention, partial drafts, stale revisions, Stop and resume. Then run the user's real request on a chosen actual model with controlled source fixtures: inspect content for completeness, tailored differences, practical rehearsal use and unsupported facts. Fake models prove tools/recovery only. Cost and time must be reported as measurements, never guessed.

The app's dark chat palette is not the PDF's paper theme. Include title, date, contents links when long, and page numbers; keep provenance/unknowns readable. Choose fonts supporting the document language and embed or load them in a controlled way. Do not use screenshots of chat as the PDF.
2. Implement actual pagination: headings stay with following content, short callouts/dialogue groups can stay together, tables repeat headers and wrap cells, oversized tables/blocks can split, URLs/long words wrap. Never apply break-inside:avoid to an entire long section/table and create blank pages or clipped content. Landscape is optional only when genuinely needed. No fixed-height page containers that crop overflow. Reserve footer/header space.
3. Render server-owned HTML with scripts disabled/absent and external requests blocked except controlled fonts/assets. Resolve only explicitly authorized media; render must not fetch arbitrary links from an uploaded document. Escape titles/header/footer fields. Use HTML input rather than logging into an app URL or forwarding user cookies to the render service.
4. Publish queues the frozen revision; return the source preview immediately. Existing activity reports real states, e.g. 'Writing the rehearsal guide', then 'Preparing PDF'. Rendering releases the workspace agent slot once publication is durably queued. Another message can be accepted while rendering. Persist public ready/failed activity before notification; link the artifact to its originating run/message even if newer replies arrived. Recovery comes from durable state and existing catch-up, not a new permanent polling loop.
5. Render jobs claim a bounded attempt, read the immutable source, call Browser Run, store output bytes in private R2, then conditionally publish ready metadata if attempt/visibility are still valid. D1 and R2 are not one transaction: deterministic keys plus claim checks and existing cleanup must handle a crash after upload and an orphaned output. Duplicate Queue delivery must not publish twice or render an already-ready revision again. Recheck author access after external rendering; stale/deleted/inaccessible work cannot be published. Use existing bounded retries; honor throttling without rebuilding content.
6. Chat shows one artifact card: title, type and real state; Open and Download when available. During render Open source preview; PDF download becomes enabled only when bytes exist. A failed render has Retry PDF, retaining content; no regeneration/provider spend for that retry. Revision cards clearly identify newer/older versions; don't mutate the old attachment under an existing message.
7. Open uses the existing authenticated blob path and gallery where useful. Offer readable HTML/Markdown preview as the mobile/browser fallback if native PDF embedding fails; always retain download/open-in-system-viewer access. An empty iframe is not successful preview evidence. Preserve current workspace/account changes, blob revocation and no-private-cache rules. Markdown export is the same source, not a second model-generated answer.
8. Include generated source/output/metadata in existing cleanup/export/erasure inventory. Preserve originals and prior versions until the supported lifecycle removes them; don't reuse the 14-day unretained upload expiry for published documents without an explicit lifecycle rule. No new private-note or sharing feature is implied.

### Repair re-audit, 2026-10-11 — source findings

No application source edits were made in this review.

- **DR01 / P1 / source-confirmed / S:** `inbox/repository.ts` checks whether document media is already linked before checking the message's immutable transport ID/fingerprint. After a successful acceptance whose response is lost, the identical retry is rejected as "already sent with another message" before its existing message/run can be returned. Replay an authorized matching acceptance first; keep reuse by a different message forbidden. The document availability/ownership preflight also still lacks the image-style in-transaction media guard. Document attachments are rejected on steering while the ordinary composer supports follow-ups during work: either support that path with retained source IDs or make its user-facing behavior explicit without dropping files.
- **DR02 / P1 / source-confirmed / M:** render metadata publication remains two separate writes: output-media INSERT, then revision UPDATE. Cleanup handles only a zero-row UPDATE, not exceptions/crashes between writes. The completion UPDATE checks attempt ID but not current rendering state/lease/source: the timeout owner can mark an attempt failed without changing its ID and its late completion can still mark it ready. Moreover, the same outer catch includes `recordDocumentActivity` after successful publication, so an activity failure turns an already-ready PDF into failed. Use one aborting conditional metadata batch, check the actual current attempt/state/source, and separate notification recovery from render failure. Reuse existing owners; no new service is needed.
- **DR03 / P1 / source-confirmed / M:** start idempotency applies only to creation without `document_id`, and the repository lets a model-supplied key override the trusted logical action ID. Revising an existing document still allocates a random revision on every replay; new draft revision numbers derive from the last published revision, so concurrent drafts can receive the same number. No payload-matching durable receipt protects section/publish effects. Use trusted action identity for every authoring effect, bind replay to its immutable payload, and allocate revision order at the existing D1 owner. Structured manifest inheritance fixes section reconstruction, not crash-safe authoring.
- **DR04 / P2 / source-confirmed / S–M:** activity IDs are `${runId}_doc_${revisionId}_${renderState}`, so later transitions back to an already-recorded state cannot publish a fresh cursor/payload. Merge canonical recovery per document/revision and issue a new durable transition identity when state/output changes. **Considered and rejected:** cross-chat fallback state leakage is prevented in the production route by the keyed Transcript; do not report it as a production defect. Reattaching recovered documents to the last arbitrary visible run still gives incorrect placement when their original run is outside the page.
- **DR05 / P2 / source-confirmed / S:** DB export/erasure inventory now includes generated-document stores, but `routes/workspaces.ts` still inventories R2 only from media and extraction rows. Generated `*-draft.json`, `*-source.md` and `*-manifest.json` keys are outside that inventory and survive workspace erasure. Inventory these private source keys before deleting D1 rows and retain a bounded cleanup path for failure/in-flight output. Do not treat DB cascade coverage as byte erasure.
- **DR06 / P1 / source-confirmed / S–M:** long-paste recovery is conditional on the ordinary stored draft being an empty string. If surrounding instructions remain, reload returns those instructions and ignores the saved paste; if recovery does run, it restores the oversized paste into the textarea rather than reconstructing the ingestible attachment, leaving Send disabled by the same character limit.
