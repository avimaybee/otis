# Otis latency and efficiency audit — 2026-10-06

Status: initial audit complete; prioritized recommendations and reproducible checks below. Production latency remains unmeasured. Keep appending dated observations during implementation.

Baseline: commit `dd407e1` plus the existing uncommitted provider/voice changes. Source code is being inspected without modification. Documentation is used for product intent, not as proof of correct or incorrect implementation.

Goal: shorten send-to-first-visible-answer and send-to-completion, reduce unnecessary Worker/D1/provider work, and improve conversational UX using the current stack. No new infrastructure, ORM, vector store, or broad rewrite.

Evidence labels: **confirmed** means the live code proves the behavior; **measured** means a reproducible local check observed it; **investigate** means runtime/provider evidence is still needed. No production latency numbers will be invented.

## Running observations

- Initial inspection: existing uncommitted changes touch provider capabilities and voice capture. Preserve these and inspect the working tree rather than assuming HEAD represents the application.
- Verification commands available in root package.json: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`. This audit is documentation-only; application checks will be reported only if actually run.
- Discovery 1: live text delivery is database-gated. `publishAgentActivity` does an awaited dedupe SELECT, a two-statement write batch, and an awaited cursor SELECT before broadcasting (`apps/worker/src/agent/activity.ts:17-42`). Each preview chunk therefore costs three serial D1 calls and updates two rows. This is confirmed code behavior, not a measured production timing.
- Discovery 2: `StreamPublisher` waits for a 2,048-character size threshold or a 400 ms timer before publishing text (`apps/worker/src/agent/streamPublish.ts:29-32,96-101,152-155`). The first token is not immediately visible. The exact timer scheduling delay is still being traced.
- Discovery 3: production SSE is not entirely push-only: its heartbeat rechecks membership and reads activity from D1 (`apps/worker/src/chat/stream.ts:246-291`). Initial catch-up also precedes live subscription, leaving a possible missed-event window (`:201-234`); investigate whether this explains delayed delivery before reducing recovery reads.
- Discovery 4: ordinary acceptance chooses the Queue before the already-bound workspace actor (`apps/worker/src/dispatchHint.ts:18-45`). Wrangler specifies batch size 10 and no batch timeout. Queue startup latency and whether its consumer runs in the same place as SSE need immediate verification; direct actor wake-up already exists as fallback.
- Discovery 5: context retrieval executes independent reads serially, loads every suppression ID, scans every entity name for every nonempty message, and performs another read for each matching entity (`apps/worker/src/agent/context.ts:98-113,166-173,234-274`). This affects even greetings. Use a scoped read batch, SQL suppression filtering, and bounded entity matching instead of adding caches or a vector service.
- Discovery 6: repeated membership/model/credential reads exist across acceptance, dispatch, handler setup, model selection and each provider round (`apps/worker/src/inbox/repository.ts:524`, `apps/worker/src/actor/dispatch.ts:957-962`, `apps/worker/src/agent/handler.ts:143-164`, `apps/worker/src/providers/service.ts:153-181,234-242`). Consolidate within each trusted execution boundary; keep authoritative membership checks at acceptance and mutation boundaries.
- Discovery 7 (highest priority): the normal Queue consumer executes `dispatchWorkspace` in the Queue Worker (`apps/worker/src/index.ts:963`), while browser SSE is forwarded to the workspace Durable Object (`apps/worker/src/routes/activity.ts:51-54`). `liveChatBus` is a module-local Map (`apps/worker/src/chat/liveBus.ts:20`), not a cross-runtime transport. The normal path does not intentionally share subscribers with the producer. SSE's 15-second activity catch-up (`packages/contracts/src/chat.ts:122`, `apps/worker/src/chat/stream.ts:272-291`) can therefore be the mechanism delivering the reply. Directly dispatching through the existing workspace actor resolves both the transport mismatch and Queue wait without new infrastructure. Production timing remains unmeasured.
- Discovery 8: `getTurnContext` is called anew for every provider round (`apps/worker/src/agent/handler.ts:442`), including linked Gemini tool continuations. Even unchanged context is reread. Reuse context within an execution slice until a business write or new steering input invalidates it; do not replace D1 with an authoritative in-memory cache.
- Discovery 9: context has an unbounded candidate collection followed by insertion-order truncation: workspace notes occupy the list before relevant member/entity/FTS notes (`apps/worker/src/agent/context.ts:191-320`). Reading relevant notes can still fail to include them in the prompt. Rank relevant scoped notes before the final limit and bound input size; performance and answer quality improve together.
- Discovery 10: Cloudflare's current official Queue documentation confirms omitted `max_batch_timeout` defaults to 5 seconds ([batching](https://developers.cloudflare.com/queues/configuration/batching-retries/)). The repository's Queue-first path inherits this setting. This is a configured potential wait, not a measured constant on every request.
- Discovery 11: Otis sets Gemini 3.5 Flash-Lite's default thinking choice to **medium** (`packages/agent/src/providers/registry.ts:173`); Google's current [thinking documentation](https://ai.google.dev/gemini-api/docs/thinking/) lists its native default as **minimal**. The model snapshot-to-request path is being checked before calling this an effective slowdown. Preserve explicit user-selected effort; change only the default for routine capture if verified.
- Discovery 12: frontend stream errors always close the EventSource and wait 1.5 seconds before full snapshot recovery (`apps/web/src/hooks/useActivityStream.ts:71-90`), rather than using incremental reconnect. Source also schedules additional run/message refreshes after sending. Inspect event-to-fetch behavior before recommending removal of the fallback.
- Discovery 13: Gemini retries every linked-continuation HTTP 400 once as a full stateless request (`packages/agent/src/providers/gemini.ts:393-428`), including errors unrelated to an expired continuation. Restrict fallback to verified continuation errors and report the actual retry error; avoid silently doubling invalid requests.
- Discovery 14: the browser has a repeated recovery fetch, not just one fallback: its 2.5-second timer depends on the `running` object, and each run refresh replaces that object (`apps/web/src/ConversationScreen.tsx:348-356`, `apps/web/src/api/snapshot.ts:76-82`). This can mask broken SSE, but adds run/transcript reads and makes the user wait for polling to see updates. Treat the 15-second SSE catch-up and 2.5-second UI fallback as overlapping mechanisms, not additive fixed delays.
- Discovery 15: after every successful send the client invalidates the entire chat snapshot (`apps/web/src/ConversationScreen.tsx:440`). A snapshot performs four parallel HTTP reads followed by a request for every run in the loaded transcript (`apps/web/src/api/snapshot.ts:34-48`). Long chats therefore incur an HTTP N+1 and re-download old activity on every send/resync. Patch the acceptance into the existing cache and refresh only the new run; load historical run details on inspection.
- Vetting correction to Discovery 11: the registry's `defaultChoiceId: 'medium'` is **not applied by message acceptance**. With no explicit chat effort, `resolveThinkingSnapshot` persists `{kind:'provider_default'}` (`apps/worker/src/inbox/repository.ts:249-268`), and the adapter omits `thinking_level`. Do not present medium effort as the cause of this user's Flash-Lite latency. Google's documented native default is already minimal.
- Discovery 16: the test named dispatch promptness calls `dispatchWorkspace` directly (`apps/worker/test/dispatch-promptness.integration.test.ts:139-140`). It verifies durable execution, but does not cover configured Queue batching or a Queue-producer/DO-subscriber streaming topology. A passing test here cannot establish production send-to-first-token latency.
- Discovery 17: every ordinary ledger mutation loads the entire workspace projection and snapshots all its maps before executing (`packages/ledger/src/repository/executor.ts:819-823`). `set_fields` repeats this whole boundary for every field (`apps/worker/src/agent/repository.ts:773-795`). Investigating exact table/read counts; this is a scaling bottleneck independent of model speed. Keep prepared SQL and the ledger; load only command dependencies rather than replacing the backend.
- Discovery 18: tool bookkeeping serializes receipt checks, daily count, step lookup/all-step listing, step persistence, revision read, public step-start publication, actual tool, step completion, public step-finish publication, and progress checkpoint (`apps/worker/src/agent/handler.ts:809-987`). Each public step event uses Discovery 1's three-call publication. Batch adjacent bookkeeping and return commit metadata; independent **read** tools can be batched, dependent business writes should remain ordered.
- Discovery 19: the stable system prompt hardcodes Kerning (`packages/agent/src/prompt.ts:17`) although the dynamic context already provides workspace name (`:59`). This can make another workspace receive wrong-business answers. Replace that one baked-in name with workspace-neutral wording; no architecture change required.
- Architecture follow-up requested by user: consult current Cloudflare documentation and compare Workflows, Queues, Durable Objects, D1 placement/batching and real-time transport. Recommendations must explain what existing work each service removes, its latency/cost tradeoff, and why adopting it would be simpler than the current implementation.
- Discovery 20: persisted lifecycle events are not consistently broadcast at all. `completeRun` appends a full-answer `text_chunk` and `run_finished` to its D1 batch (`apps/worker/src/actor/dispatch.ts:507-523`), but the actor dispatch module has no `liveChatBus` publication. Acceptance and ledger action events similarly have durable-only publishers. Even after moving generation into the actor, explicitly publish **committed** lifecycle events there; otherwise completion/UI reconciliation still relies on catch-up and refresh timers.
- Discovery 21: Queue messages are processed serially across workspaces, including full provider turns (`apps/worker/src/index.ts:936-977`). One slow workspace can hold up later messages in that batch. Forward queue recovery notifications to their existing actors with bounded concurrency; coalesce duplicate workspace hints within the batch. Do not parallelize mutations inside a workspace.
- Discovery 22: the projection loader reads seven complete tables serially (entities, aliases, entity_state, tasks, draft_projections, memory_entries, memory_suppressions; `packages/ledger/src/repository/queries.ts:167-368`). It does **not** replay the whole event history on ordinary writes. The correct fix is first batch reads, then introduce targeted command inputs incrementally, preserving deterministic reducers and commit atomicity.
- Discovery 23: Stop updates D1 but does not notify the running provider or actor (`apps/worker/src/routes/runs.ts:229-233`, `apps/worker/src/actor/dispatch.ts:1712-1744`). The provider input has no abort signal (`apps/worker/src/agent/handler.ts:569-590`), although adapters accept one. In-flight generation can continue until completion/60-second timeout and keep publishing preview text; `publishAgentActivity` does not check run status, membership or current attempt. Use the actor's existing run owner to abort locally after durable Stop, and refuse stale public events. Test stop-during-stream and stop-then-new-message.
- Discovery 24: claiming a workspace lease currently reads, conditionally updates, then reads again (`apps/worker/src/actor/leases.ts:77-98`). A scoped conditional `UPDATE ... RETURNING` can return the fence/expiry directly. Keep the existing fencing semantics until execution owners are consolidated; this is a small SQL simplification, not a reason to add or remove a consensus layer.
- Discovery 25: frequent step allocation downloads all previous step results just to calculate an index (`apps/worker/src/agent/handler.ts:866-867`, `apps/worker/src/actor/steps.ts:363-370`). Use a scoped `MAX(step_index)+1` or allocate/return the next index atomically; preserve gaps and unique constraints rather than assuming row count equals next index.
- Discovery 26: name-resolution candidate reads are bounded, but return full fields for every ranked candidate even when the model only needs the winning entity ID (`apps/worker/src/agent/repository.ts:202-252`). Prefer compact match metadata and fetch fields for the selected entity when needed. Keep ambiguity evidence; do not choose a lead merely to save one model call.
- Cloudflare architecture evidence (2026-10-06): [Workflows](https://developers.cloudflare.com/workflows/get-started/guide/) provides durable steps, retries and waits, but [Free pricing](https://developers.cloudflare.com/workflows/reference/pricing/) includes only 3,000 steps/day and 10 ms CPU/invocation. It is a potential simplification for long-lived background jobs, not evidence that a chat token will arrive sooner. [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) bills active wall-clock duration; persistent SSE/timers prevent idle hibernation. Hibernating [WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) are a separate optional cost improvement, not required to fix the current route.
- Discovery 27: database catch-up is paged (200 activities), but initial SSE catch-up reads only one page and then subscribes to potentially newer live events (`apps/worker/src/chat/activity.ts:32-34,62-66`, `apps/worker/src/chat/stream.ts:201-239`). A newer live cursor can advance past unread history. Catch up fully with a bounded buffered subscription before applying newer live cursors; never use `latest_cursor` as proof that every earlier page was applied.
- Discovery 28: [D1 Free limits](https://developers.cloudflare.com/d1/platform/limits/) also include **50 queries per Worker invocation**, separate from daily row limits. Repeated setup/tool/stream calls can hit an invocation budget long before 5M daily reads. Count SQL statements as well as network calls: batching reduces roundtrips, not the number of SQL statements or scanned rows.
- Discovery 29: holding a DO SSE connection open with timers keeps it active, even while the user is idle ([lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)). Free DO duration is 13,000 GB-s/day at 128 MB/object ([pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)): roughly 100,000 active object-seconds/day, about 28 object-hours, or 1.2 permanently active objects. This is capacity arithmetic, not measured usage; concurrent connections to the same object share its duration. For two people sharing one workspace this can fit, but always-open tabs across many workspaces will not scale on Free. First suspend idle/hidden SSE and reconnect from cursor on foreground/send; consider hibernating WebSockets if persistent presence becomes necessary.
- Discovery 30: switching the immediate wake-up to `ctx.waitUntil(stub.fetch(...))` alone must account for the [Worker's 30-second post-response lifetime](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/), while provider rounds allow 60 seconds. The actor must own continued execution/liveness and durable recovery; do not fire-and-forget work in an ordinary Worker or drop the only awaited actor request. Keep Queue/cron as backstops and verify disconnect/long-turn behavior.

## Recommended Cloudflare architecture

Keep the current services initially and change their responsibilities:

```text
Browser: immediate local echo + stable UUID
  -> Worker: scoped validation + one durable input/run/outbox acceptance
  -> workspace Durable Object: immediate bounded execution, same live subscribers
       -> batched D1 context reads
       -> direct provider stream -> existing SSE -> browser
       -> ledger transactions at actual business writes
       -> atomic final conversation/run commit -> immediate completion event

Queue/cron: retries, recovery and genuinely deferred work -> that same actor
R2: private audio and exports
```

The actor is the execution and live-publication owner; D1 remains durable business/conversation truth. Do not relocate all data or introduce a second authoritative state store to fix a transport mismatch. There must be only one intended writer/executor per workspace, with existing D1 atomic preconditions/receipts covering restart and duplicate delivery.

Actor liveness has a concrete lean option: the actor schedules its bounded execution promise using **its own** `state.waitUntil`, returns the wake-up acknowledgment promptly, and clears its local in-flight reference on settlement. Cloudflare's current [state API](https://developers.cloudflare.com/durable-objects/api/state/) documents eviction prevention until settlement or up to 15 minutes, separate from ordinary Worker's 30-second post-response window. Existing D1 inputs/checkpoints/outbox still enable recovery after process loss. Do not block the whole object with `blockConcurrencyWhile` during a model call: Send, Stop, SSE and clarification events need to remain serviceable. Verify this with real local DO/D1 and a long-turn/disconnect check; the source currently does not implement it.

For preview delivery, stage the change:

1. Immediately improve first-flush timing and use one guarded/idempotent D1 batch per coalesced persisted activity, returning its cursor. This retains the existing activity contract while eliminating two network waits per chunk.
2. If measurements still show preview persistence dominating, give **transient text preview** a distinct run/round/sequence event and stream it directly from the actor. Persist final text, receipts and semantic activity; reconnect from durable state instead of retaining every token. This requires a coordinated shared event/client update. Keep provider public summaries and business activity durable before publication; do not silently make all existing activity ephemeral.

## Considered and rejected

- **Flash-Lite medium thinking as the explanation:** rejected. Registry metadata says medium, but acceptance stores provider_default when no override exists; the adapter omits thinking_level. Current Google documentation says native minimal. Preserve explicit effort choices and inspect a run snapshot if a user has overridden them.
- **Another model/router/classifier on every message:** rejected as an initial optimization; it adds a model roundtrip before the useful call.
- **Lower maxOutputTokens automatically makes any reply faster:** rejected. A cap is not a demand to generate that many tokens; tune observed output/effort, do not truncate useful answers blindly.
- **New ORM/vector database, global business cache, second agent service, transport polling at a shorter interval:** rejected. None is needed to fix the proven route and read-volume issues.
- **Delete all guards/receipts/ledger history to save writes:** rejected. Simplify redundant bookkeeping while retaining atomic failure, scoped authority and retry idempotency. D1 is already ACID; no new artificial consensus tables are justified.
- **Rewrite backend to Workflows or actor SQLite before measuring this route:** deferred. Potential code simplification/storage locality does not establish an immediate latency benefit and carries migration cost.

## Product direction options

These are improvements to the existing capture/memory conversation, not a CRM expansion:

- Show meaningful milestones using existing message metadata: local capture, server received, actual saved changes or the one missing detail. Publish these from committed receipts; keep a new follow-up sendable while the previous answer is active. F01/F03 make this cheap and truthful.
- After roundtrip reduction, examine whether common known-lead capture needs multiple model turns solely to turn a name into an ID. If representative traces prove it does, let existing write tools accept a scoped entity reference resolved deterministically to an unambiguous match. Keep ambiguous names as questions. Avoid a broad new generic capture API or a separate classifier.
- Use a corrected memory ranking to put the most relevant remembered fact in the first answer. Measure fewer repeat questions/tool calls on real capture examples before adding another retrieval technology.

## Scope and limitations

Primary focus: browser send → Worker acceptance → dispatch/actor → context/provider/tools → streaming and completion. Secondary focus: backend read/write economics, correctness that causes retries or wasted work, voice/Telegram, and lean product opportunities.

This was a hotspot audit, not a complete security, dependency, visual/accessibility, scheduler/brief/export, database-migration or device audit. Intent documents informed scope only; findings come from current source or explicitly labeled external/runtime evidence. No subagents were invoked. The next eligible work is implementation of the conversational route optimizations with real DO/D1/stream evidence, not a claim that a product release gate is complete.

No production business writes, provider calls charged to user credentials, deployment, commits, pushes, or source edits are part of this audit.
