# Otis: independent UI, reply and responsiveness audit

Status: independently audited; implementation recommendations specified. Baseline: `2d2c0c1`, 2026-10-07; working tree initially clean. Concurrent source fixes through `06ee63c` were reviewed separately; they are not changes made by this audit.

This pass uses current source and rendered behavior, not previous audit claims or plan completion labels. The user's current direction is compact, cohesive desktop UI with Otis's own character, and a root review of replying to Otis. Existing charcoal/Highlighter foundations inform the recommendations; old inflated spacing and 44px visual recipes do not override this direction. Source remains unchanged during the audit. No subagents.

## Running observations

1. **Reply mode silently selects a pending question.** `apps/web/src/ConversationScreen.tsx:413` selects the first answerable pending clarification unless dismissed; `activeClarification` defaults to it without an explicit Reply action. `:623` attaches that clarification ID to an ordinary text send. The live conversation shows an old media question in the composer while the latest answer is “Yeah, I'm here. What do you need?”. This is semantic routing, not only a styling problem. Next: verify dismissal, navigation, text/voice consistency and server handling without resolving real business work.

2. **The current reply control is a clarification answer control.** `Composer.tsx:26` accepts `ClarificationContext`, and `Transcript.tsx` exposes `onReply` only for `pending_clarification`. Normal Otis responses have Copy but no Reply. The initial generic-message-reply interpretation was withdrawn after the user's clarification and screenshot: they want Codex-style question panels, not quoted-message replies. Do not add a generic reply feature based on this observation.

3. **Vertical whitespace has multiple owners.** `apps/web/src/index.css:58` gives the transcript column a 24px gap, `:64` gives message groups another 24px gap, and invisible hover action rows remain in layout (`:91`–`:101`). Working disclosures introduce their own height/gaps. The supplied screenshot shows short messages separated by large blank regions. Next: measure actual rendered contributions rather than attributing all whitespace to buttons.

4. **Current Button primitives already have 32/36px sizes.** `apps/web/src/components/ui/button.tsx` uses `h-8`, `h-9`, `size-8`, `size-9`; blanket shrinking of every Button would miss the bigger composition issues. Sidebar actions, source links, working rows and several other CSS controls independently retain 44px minimum heights. Desktop density and mobile touch reach should be specified separately, with nonoverlapping hit regions.

5. **Dismiss can alternate indefinitely between old questions. Reproduced live.** The first X replaces the media question with an older client/currency question. The second X brings the media question back. Only one `dismissedClarificationId` is stored, so excluding B makes A eligible again. Neither click leaves an ordinary composer. Navigation also resets this exclusion (`ConversationScreen.tsx:153`, `:185`); acceptance resets it (`:532`). This is a high-priority interaction bug. No answer was submitted or business work resumed during the reproduction.

6. **Text and voice disagree about reply intent at the initial baseline.** Text outbox entries carry `activeClarification.id` (`ConversationScreen.tsx:623`); voice entries carry only media identity (`:661`–`:668`). The initially inspected composer displayed the reply banner with the voice control present, so a spoken answer could become a separate run. Concurrent commit `06ee63c` now hides the mic while replying and adds a regression; the current conversation suite passes 35 tests. This removes the misleading local affordance, but does not implement voice answers. A future panel mic needs a controlled end-to-end targeted-transcription fixture, not a test against the real pending business question. Deployment was not verified.

7. **Measured whitespace: hidden actions consume 32px per turn, plus a 4px turn gap.** In the current 1526×686 CSS-pixel desktop viewport (DPR 1.25), a one-line Otis answer occupies 60px: 24px text + 4px gap + an invisible 32px action row. A one-line member bubble occupies 76px: 40px bubble + 4px + 32px hidden actions. The 24px transcript/group gaps add further separation. Thus hiding actions with opacity does not make the transcript compact. Measured composer height is 168px with the stale reply bar; the actual input surface is 96px, including a second controls row. These are browser geometry measurements, not happy-dom layout claims.

8. **Clarifications are chat-scoped on the server.** `apps/worker/src/routes/clarifications.ts:89` filters workspace and chat and sorts newest-first. The media question is old state inside this conversation, not evidence of cross-chat leakage. Reject that hypothesis unless new evidence appears.

9. **The clarification route takes precedence over commands.** `apps/worker/src/routes/chats.ts:318` delegates a payload with `clarification_id` before parsing `/commands`; Composer also bypasses command handling in reply mode (`:252`). The stale automatic selection therefore changes the meaning of ordinary command input too. The answer route requires text/resolved fields and does not consume audio/image identities (`routes/clarifications.ts:176`–`:202`), so merely copying the clarification ID into voice entries is insufficient.

10. **The first-text and catalog fixes are present in current source.** `agent/streamPublish.ts:133` sends the first transient frame immediately; later frames use a 100ms handler timer. `agent/context.ts:394` derives available models from workspace credential status/platform presence and includes supported effort choices. Acceptance/answer events now patch local messages; old-run details are batched. These retire the corresponding old implementation gaps locally, without asserting the same version is deployed. Targeted suites passed 67 tests (39 web, 28 worker/pure).

11. **Chat opening still waits for secondary run details.** `apps/web/src/api/snapshot.ts:40` starts four independent reads, then awaits `api.runs` before returning messages (`:50`–`:74`). Batching eliminated request fan-out but did not eliminate this waterfall. Render the useful transcript as soon as the primary message/chat reads succeed, then fill Working/history metadata; do not require another framework or a new all-purpose snapshot endpoint.

12. **Context caching invalidates after every completed read tool too.** `agent/handler.ts:548` keys reuse on total completed-tool-result count, which grows at `:1301` and is not reset when a round completes. Normal multi-round requests therefore reassemble context even after read-only tools. Reuse immutable context within a bounded slice after reads, invalidating for steering and actual writes/current business revision. Preserve fresh code authorization and mutation preconditions; do not replace them with cached authority.

13. **Round close still persists text in sequential 2048-character pieces.** `agent/streamPublish.ts:277` drains each chunk with an awaited publish; each publish performs its own two-statement D1 batch (`agent/activity.ts:21`). A 10,240-character response has five serialized publication roundtrips before the final committed reply path. This no longer blocks first text, but still affects completion latency and write count. Consider one bounded per-round text record or one grouped batch for existing records, preserving interrupted previews/reconnect and receipts. Measure first; do not silently delete recovery evidence.

14. **Green design/story checks do not cover these interactions or geometry.** `pnpm check:design` passes (92 files), and `pnpm check:stories` passes (92 fixture IDs in 17 files). The initial clarification test mounts Composer and checks that `onCancel` fires (`apps/web/test/conversation.test.tsx:107`); it did not exercise ConversationScreen's two-question selection, and the initial browser-loaded version reproduced the dismissal loop. Concurrent `95551ee` added selector regressions and repaired that algorithm locally. Screen-level submission ownership and rendered spacing still need verification; more mock callback tests would not establish them.

15. **Narrow-width reply context hides the information needed to answer safely.** At 390×844, the one-line reply question truncates before its meaningful ending. The composer consumes 168px and leaves an unobvious distinction between an old pending operation and the latest response. The new question panel should show the meaningful question across multiple lines and keep ordinary chat independent, with a way to inspect the original request.

16. **User clarified the exact target: Codex's question panel.** Their [reference screenshot](qa/2026-10-07-codex-question-reference.png) shows numbered suggestions, a separate free-text answer, Send/Skip/close, and an ordinary composer underneath. Keep the question target bound to that panel's submission. Main chat must never inherit it. Skip can defer an Otis operation without guessed business writes; the original pending callout remains reachable.

17. **Concurrent cumulative-dismissal fix reviewed.** Commit `95551ee` replaces the single exclusion with `dismissedClarificationIds` and adds `selectPendingQuestion` plus regressions. The updated conversation suite passes 35 tests. This retires the alternating-dismissal algorithm locally. It still automatically selects a question for normal chat, resets dismissals on navigation/acceptance, and uses one chat draft as the answer field. The root question-panel recommendation remains; deployment of this commit was not verified.

18. **Answer drafts and late acceptance have no independent question owner.** Candidate buttons write into the main draft; switching/closing the reply context does not establish a new question-scoped draft (`Composer.tsx:324`). After HTTP acceptance, `ConversationScreen.tsx:531` clears reply selection and all exclusions for the view, even if the user has since opened another question. Rapid follow-ups can also capture the same old clarification before the first answer is acknowledged. These are source-traced recovery/routing hazards, not additional live business-answer tests. The new plan captures immutable question intent at local submission and clears only the matching target.

19. **Normal confirmations expose implementation identifiers.** The live transcript displays “Logged quote event for entity 'ent_…' saved”. `packages/ledger/src/commands/logEvent.ts:142` creates the raw summary; `Transcript.tsx:466` renders it via `formatOutcomeSummary`. Make the normal receipt concise and human-readable from existing data; keep technical IDs in inspection. Avoid another entity fetch per receipt or rewriting historical ledger events.

20. **Context batching still downloads every workspace entity name.** `agent/context.ts:135` has `SELECT id, name FROM entities WHERE workspace_id = ?` with no bound. Matching runs in JavaScript and stops after five matches (`:244`), which does not bound rows already downloaded. A greeting with no match examines every entity; multi-round read tools invalidate the context cache as noted in observation 12. Prefer bounded matching/referenced entity IDs using existing SQL/search capabilities, not a vector database, extra LLM classifier or arbitrary UUID cap that drops relevant names. Production row/CPU savings require measurement.

21. **Snapshot cancellation is still unconnected.** `useChatSnapshot` invokes `fetchChatSnapshot` without consuming the query's AbortSignal; `getChat`, `listMessages`, `activity`, `runs` and `clarifications` don't accept one. Their internal request timeout is not navigation cancellation. Thread the signal into disposable reads so rapid chat switches can stop unwanted response work, while keeping durable outbox sends alive. This is a source finding; no network-cancellation benchmark was run.

22. **The visual study makes the proposal concrete.** Native browser checks confirm separate question/main inputs, free-text override of suggestions, question Send, Skip/reopen and answer-field focus. [Recorded geometry](qa/2026-10-07-study-geometry.json) shows a 56px desktop composer and 76px narrow mobile composer, no horizontal overflow at 360, 390, 900, 1280 and 1440px, and a roughly 216–220px short-question panel. The study uses the actual installed Instrument Sans font and Otis's charcoal colors; it makes no production-component, business-resume or device-keyboard claim.

## Architecture and validation boundary

Keep the existing Worker/actor/D1/live-stream arrangement for interactive turns. The first-preview fix now bypasses D1 and uses a 100ms cadence; adding Workflows to normal chat does not remove the remaining source-traced waits. Cloudflare [Workers Streams](https://developers.cloudflare.com/workers/runtime-apis/streams/) supports direct streaming. Use existing durable facilities for background recovery where appropriate, not another interactive orchestration layer.

The question UI needs explicit target identity and local submission ownership, not a new question service or generic reply schema. Text answers can use the existing clarification route/outbox. Voice needs a real targeted-transcription/resume path; the current queued-run-only transcript guard prevents a superficial client-only fix.

This audit did not rerun full typecheck/lint/test/build or Storybook build, because application source was not changed by the auditor. It ran the named targeted suites, design/story inventory checks and native-browser tests. It did not verify provider latency percentiles, production deployment/CPU/D1 totals, actual phone codecs/keyboard behavior, all application flows or a security audit. The next eligible work is the two specified UI/question plans, with full implementation gates and identified-build browser evidence.
