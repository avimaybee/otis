## 1. Implemented behavior with concrete scenarios

- **One flush owner per browser/account** (`apps/web/src/api/flush.ts`, owned by the mounted `ConversationScreen` via registration): retries what is still unsent on mount, after sends, on `online`, on visible-foreground return, and on a bounded timer for deferred entries. Per-chat chronological order with blocking: a chat's walk stops at the first entry whose acceptance is still unknown and not attemptable now, so newer inputs wait rather than posting out of order; explicitly resolved entries (saved, permanent/exhausted failures) skip without blocking. Local acceptance (echo, draft clear, follow) stays instant in `send()`; network acceptance dispatch joins the same per-chat/claim path, so a follow-up submit never overtakes a still-unacknowledged first POST while the composer never blocks. No global in-flight flag exists: a transport that never settles must never wedge the owner (same-UUID reentrancy is fenced by the per-UUID delivery claim plus per-pass attempted sets).
- **Retry discipline**: transient (network failure without HTTP status, 408/425/429/5xx) schedules one bounded automatic retry each — exponential backoff (`FLUSH_BACKOFF_BASE_MS` 2s, cap 5min on our own delay) honoring a server `Retry-After` newly surfaced as `ApiError.retryAfterMs` (delay-seconds or HTTP-date; valid server instants are authoritative up to a documented 24h parsing bound, never shortened by the exponential cap). Permanent failures (400/401/403/404/409/422, including obsolete clarifications) stay failed with their attached Retry/Discard and never reroute. Automatic retries stop at `FLUSH_MAX_ATTEMPTS` (8); explicit user Retry is never capped.
- **Cross-tab claims without a lock service**: the flushing tab holds a short exclusive claim — Web Locks `ifAvailable` where present, else a 30s-expiry timestamp claim acquired, renewed and released inside single IndexedDB readwrite transactions (store-level serialization makes concurrent acquirers converge; owner-token guarded release; atomic compare-and-set renewal). Claim transactions resolve only on transaction commit — a put that "succeeds" followed by an abort reports failure, never a phantom claim. Work re-verifies live ownership before every POST after the first and stops on renewal loss; a lost lease is never silently re-taken. A denied tab skips and waits for the next wake event (no storms). Server UUID dedupe stays the final duplicate-effect protection.
- **Entry-scoped transport**: `deliverEntry` binds `createChat`/`sendMessage`/refreshes to the entry's immutable user/workspace/chat scope — a background workspace's pending entries flush in their own scope while another workspace is viewed (membership stays live via per-attempt server revalidation). UI updates (banners, navigation, draft/clarification resets) additionally require the current view; `loseAccess` only closes the view its failure belongs to. A freshness re-read after claiming means concurrent passes never POST for settled/pruned entries and never fork a new chat twice.
- **Reload recovery**: `send()` echoes with one UUID; on reload `App` rehydrates the IndexedDB snapshot and the flush owner redelivers sending/failed-due entries with original identities (proven: offline send → reload → foreground → one POST, one saved bubble, same UUID).
- **Discard is local-only**: failed bubbles gained a `Discard` button (aria-label "Discard unsent message"); accepted rows never offer it, and discarding cannot unsend (server rows reconcile through snapshots).
- **Update-before-activation draft commit** (`apps/web/src/components/UpdatePrompt.tsx`, `flushUserDraftSaves` in `apps/web/src/api/drafts.ts`): the Reload action first commits this account's pending debounced drafts to IndexedDB and awaits them — a browser reload does not promise a React unmount, so a keystroke inside the 400ms window would otherwise disappear when the new worker takes over. The flush awaits already-running writes too (a fired timer deletes its pending entry before settling), and failed fields stay dirty — retryable by retyping until commit or explicit removal — so an emptied pending queue alone never reads as safe. A send landing mid-hold, or keystrokes typed during it, are caught by bounded re-checks (one re-drain, never a loop) with no await between the final check and activation. Only a committed flush activates; failed or fenced storage holds the update with an honest toast instead. The stale "drafts live in session storage" comment is corrected to scoped IndexedDB.
- **Scoped IndexedDB drafts** (`apps/web/src/api/drafts.ts`): one record per account holding a persisted owner generation, so purge is an atomic cleared-record write that cannot orphan keys. Every mutation carries its originating owner session (observed at keystroke/mount, replayed by debounced and unmount-trailing saves, passed as the pre-await flight by new-chat `moveDraft`); the storage transaction compares it against the persisted generation, fencing every tab — not just the purging tab's local Map. A purge bumps the generation first, cancels this tab's pending saves, and persists the cleared record (never a delete, so the generation survives); delayed writes, deletes, moves and hydration started before the purge abort instead of resurrecting private content — including a component unmount trailing-save firing after logout and another tab's debounced timer the purge cannot cancel. First observation vs purge race is explicit: a null session (instance never observed the owner) adopts the persisted generation on first read/write — this IS the authenticated session, so reload/remount hydration restores — while an already-observed session that moves means a purge landed and is dropped. Upgradeable first writes additionally require a mount hydration to have started and no own purge since capture. The composer persists debounced, flushes a trailing write on unmount, restores on mount with a null-or-match session guard, and deletes on submit; storage failure degrades to the in-memory draft without blocking typing. Logout/account/revocation purge via `deleteDraftsForUser`.
- **Scope purge**: logout, account change and revocation purge outbox entries, new-chat mappings, drafts and the flush registration/timers; delayed flush/delivery callbacks are fenced by owner identity plus the existing epoch/route guards, and hydration races still never resurrect purged content.
- **Storage failure**: memory primary retained with honest device-only state (`Sending… Keeping on this device only.`), unchanged R5 behavior, now covered for the flush path (a rejected claim write still runs once locally rather than dropping the message).
- **PWA static shell** (`vite-plugin-pwa` 1.3.0 + `workbox-window`, `strategies: generateSW`, `registerType: prompt`): precaches versioned hashed `js/css/html/woff/woff2` only (verified in the built `sw.js` precache list); `navigateFallback: index.html` with `/^\/api/` denylisted (verified in the built `NavigationRoute`); zero runtime-caching entries, so API/auth/streams/private audio/provider traffic/credentials are never cached or persisted. The production PWA wiring lives in the **root** `vite.config.ts` (the `pnpm build`/`deploy` path); `apps/web/vite.config.ts` (dev) and Storybook resolve the update prompt's virtual module to a static no-op fallback instead — Storybook's manager/preview pipelines explicitly drop the whole `vite-plugin-pwa*` family, whose precache budget rejects Storybook's own 3.3MB manager bundle. No installability manifest ships: the plugin injects default colors (white splash, foreign green theme) with no opt-out, there are no approved icon assets, and the checker forbids color literals in src — emitting it would misrepresent the approved charcoal baseline. Install prompts are therefore not claimed; the offline shell needs precache + fallback only.
- **Safe update prompt** (`UpdatePrompt`, neutral `otis-connection` recipe + ghost buttons): appears only when the new worker waits; `Reload to update` is refused with an explanatory toast while this account has unsent entries, otherwise it awaits committing pending drafts first and holds the update with an honest toast when the commit fails, `Later` dismisses, and nothing ever auto-reloads during send/recording. Activation uses the supported `updateServiceWorker(true)` path (skip-waiting + reload) — a bare reload can leave the old worker controlling the page forever. Drafts persist in IndexedDB and outbox entries resume after reload regardless.
- **Offline shell honesty**: the cached shell boots to `UnavailableScreen`, which states offline vs session failure distinctly from the device `onLine` hint, invents no session/membership/answers, and retries through the normal session path. The offline copy promises only what the shell proves — saved unsent input retries when the connection returns, nothing was sent — attempting retries without guaranteeing storage under quota failure or closed-page background delivery; it no longer claims conversations stay available (authenticated history is deliberately uncached, per the no-/api-entries shell probe). Authenticated offline states already exist (stream `reconnecting` notice, per-message delivery rows).

## 5. Remaining defects and deferred work

- Reviewer-reproduced data races, all fixed with the proofs above: (1) `moveDraft` same-record clobber → single atomic read-modify-write; (2) purge resurrection by delayed/local-only writes → persisted per-owner generation checked atomically on every draft and outbox write (unmount trailing-saves and never-persisted other-tab rows included), with no tombstone-eviction cap and no timestamp exceptions; (3) cross-tab whole-snapshot loss → per-account transactional records with union merge plus sticky per-generation tombstones for pruned/discarded UUIDs, cleared by each purge, with legacy-envelope migration; (4) first-hydration rejection after reload/reactivation → null-session first observation adopts the persisted generation (drafts `loadDraft`/Composer guard, outbox `rehydrateOutbox`/`persistUser` scoped by synchronous restore initiation), so normal reload/remount restores while genuine purge races still drop; (5) R5 input erasure during deferred restore → first-observation persist/restore adopts and merges instead of deleting, proven by a deferred-restore screen test (send before resolve, held acceptance, original UUID + bubble kept, exactly one POST). Accepted residual: per-generation tombstones persist until the next purge (bounded by one login's activity, never evicted early); a tab holding pre-logout memory keeps showing it until its next persist/rehydrate fails closed and drops it or it reloads, while storage stays clean. Cross-tab sign-out propagation itself is out of scope (no new framework): the fence is storage-level. A fresh instance's first keystroke racing its own mount hydration persists on the next keystroke at the latest (in-memory draft covers display meanwhile).
- Watch item: happy-dom ships `navigator.locks` as null, so the Web Locks path is mock-proven only; the fallback path is live-tested with real transaction semantics via fake-indexeddb. Real two-tab contention still deserves a reviewer browser pass.
- Manifest omits icons/colors by checker/token policy; OS install prompts may be limited — documented, not a defect in the offline-shell requirement.
