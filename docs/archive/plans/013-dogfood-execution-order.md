# Reviewer execution order: prove the useful conversation first

Author: Codex reviewer, 2026-10-04. Applies to the existing dirty tree on `663f0b3`. This is a delivery-order correction, not a new numbered gate, permission to deploy, or a claim that incomplete channels work. It supplements `013-dogfood-loop-review.md` and takes precedence over older foundation-first sequencing in the plans index.

## Decision

Build one complete field-use interaction before expanding foundation work. The immediate product evidence is a linked member sending a Telegram text, receiving an actual answer promptly, saving explicit facts once, and retrieving those facts in a later message. Then add Telegram voice to that same path, followed by the member's chosen brief. Do not require every web transport, browser recording, export, callback or efficiency checkpoint before the first text journey works.

The reviewer owns architecture decisions, handoffs, work selection and acceptance. The implementation agent executes one explicitly assigned checkpoint, writes its code/tests, reports results and waits. It may point out contradictions; it must not invent product decisions, write a replacement roadmap, self-accept or start the next checkpoint. Routine naming and decomposition remain its responsibility.

## Preserve decisions and existing useful code

- Keep workspace isolation, current membership checks, durable acceptance, retry deduplication, sourced records, fenced commits and recoverable jobs. These protect even two members; do not remove them to make the demo pass.
- Clear complete facts/instructions save directly. If a separate action lacks a required date, file the clear facts and ask only for the missing detail. Accept a date-only task without demanding a clock time.
- Do not infer `warm` from interest or pick Tuesday at 10:00 from `next week`. Resolve ordinary expressions relative to the supplied timezone/date, but ask when the intended day remains ambiguous. A member may explicitly establish a durable preference; that is different from inventing one.
- Briefs remain disabled until a member chooses time, timezone, days and channel. No 08:30 or 09:00 fallback. No extra proactive outreach policy.
- Keep the approved visuals and shadcn. Do not introduce a dashboard, another composer, another ledger, another agent framework or a new service.
- Existing provider evidence is model/endpoint-specific. A configured key, registry label or passing mock is not live capability evidence. No paid inference fallback.

## What blocks progress, and what does not

Block the affected journey for demonstrated input loss, cross-workspace disclosure, wrong attribution, duplicate business effects, unauthorized writes, missing replies, misleading success, or an operating cost that exhausts the available free quota. Repair those defects in the actual path.

Do not block the journey for optional refactoring, arbitrary file size, comprehensive callback coverage, hypothetical large-team contention, a new library, or polishing an unrelated screen. Record those separately. Existing required checks still run for each source checkpoint; test the meaningful failure paths, not every imagined failure permutation.

Use a bounded task: reproduce, implement the smallest coherent repair, verify, report. If review finds another blocker, explain the concrete scenario and assign that repair explicitly. Do not silently expand a checkpoint into a subsystem rewrite.

## Execution order

### 1. Close the already-written ledger patch

015A.1 changed-only persistence is implemented and awaits independent verification. ### 2. Assign a text-only Telegram journey under 009

The reviewer must first write a source-mapped 009A implementation handoff, then explicitly assign it. Reuse current linking, inbound normalization, chats, shared commands, durable dispatch and ledger services. No second agent loop or second source of truth.

Required end-to-end path:

1. A private Telegram update from a linked member resolves the correct active workspace and author's Otis chat.
2. Persist accepted input/run/outbox before acknowledging receipt. Immediately issue the existing dispatch wake hint. Cron is recovery, not the normal request trigger. A hint failure keeps accepted work and exposes a retry/recovery condition honestly.
3. Invoke the existing selected-model agent path. An idle workspace begins promptly; contention is a real state, not a decorative queue status. Do not promise a model response within a fixed time that the provider cannot guarantee.
4. Send the actual answer or narrow clarification back to the private bot chat. Completed web chat history and Telegram output agree on the saved outcome and author.
5. A second ordinary message retrieves the earlier fact from the shared workspace records. A clarification answer resumes its existing pending operation; it does not lose the earlier facts or create another task.

The first checkpoint excludes voice, scheduled briefs, XLSX, full inline callback menus, reactions and new visual components. Keep existing typed commands working, but do not build every optional action button before natural conversation works.

Required acceptance cases: duplicate webhook produces one logical input/run/effect; storage failure is not acknowledged as accepted; wrong/revoked membership fails; model failure gives an honest retained-input outcome; known outbound failure is retryable; an unknown send outcome is not blindly retried or called exactly-once; normal idle dispatch starts without cron. Use mocked Telegram HTTP in automated tests. A real synthetic private-bot test is separate and requires the existing external-action authorization; this document grants none.

### 4. Add Telegram voice to the proven text journey

Split the existing 010 scope into checkpoints, not a new parallel STT service. First integrate Telegram OGG/Opus capture, bounded private audio retention, the verified native-audio route or Groq transcription, and the same text agent/delivery path. No raw audio/key in logs or public URLs; retained playback requires current membership.

Acceptance: a Romanian and Hungarian synthetic note each produces a usable transcript and real reply; a meaningful uncertain amount/name asks narrowly; unsupported/overlong input produces no business write; transcription failure remains understandable and recoverable. Separate mocked provider orchestration from real audio/provider evidence.

### 5. Add the chosen brief, then learn from use

Implement the selected schedule/delivery slice of 011 against actual saved tasks and promises. Reuse the Telegram outbound path. A repeated scheduler invocation must not create a second canonical brief. Unknown external send outcomes remain distinguishable. Missing items do not generate invented commitments.

Test capture -> later retrieval -> chosen-time brief with the same records. Then observe five days of actual member use: capture completion, clarifications needed, forgotten/misfiled facts, failed/slow replies and whether follow-ups are useful. Five days is an observation period, not an automatic release approval or a requirement to delay obvious fixes.

Finish additional 009 callbacks, browser voice, requested drafts/private XLSX and remaining release/device checks according to actual user value. Do not call the whole release complete after the narrow Telegram slice.
